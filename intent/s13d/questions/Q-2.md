# The running score is already shown next to the lives in the current code; is the intent out of date, or is there something the current display does not do that you want built?

The whole spec assumes the intent's premise is stale and the work is only to confirm and lock in the existing HUD with a small `hudText` helper and tests. If something else is wanted (for example the score drawn on the canvas, or a different look), the Approach and Parts sections need rewriting.

## Answer (agent:master)

Intent is stale; only lock in the existing display with tests

The intent asks for the score to be shown during play, next to the lives, and kept up to date as dots, pellets and ghosts are scored. The document finds that this already holds. `index.html` has `#score` beside `#lives` in `#hud`, and `render()` in `src/main.ts` rewrites both on every frame. Only the premise that the score shows at game end alone is out of date. The intent's own last line says scoring does not change, so nothing new is left to build. The canon criteria (CAP-4, P0-UI-009 to P0-UI-014) now describe this display, but no test binds them. Tests are the smallest change that turns the intent's behaviour into something checked. At prototype rigor, a small pure `hudText` helper plus unit and e2e tests is enough. The existing scoring tests act as the guard that nothing else moved.

Rejected:

- Wanted: score drawn on the canvas as well: The intent says to show the score next to the lives, which is the HUD. It gives no sign that a second, canvas-drawn score is wanted.
- Wanted: a different look or position for the HUD score: The intent asks for the score beside the lives, which is where it already is. Nothing in it asks for a change of styling or placement.
- Intent is stale; close the work with no code change: This would leave the in-play display, and its updates on dot, pellet, ghost, pause and end, with no tests. Nothing would stop it regressing, and the CAP-4 criteria would stay unbound.
